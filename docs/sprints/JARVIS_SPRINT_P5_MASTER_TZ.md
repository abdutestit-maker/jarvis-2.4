## 0. Как работать с этим документом (правила для агента)

1. **Ты — единственный технический руководитель этого спринта.** Пользователь оставляет ПК включённым и уходит (учёба/сон) на несколько часов. Он не будет отвечать на вопросы в реальном времени. Действуй как будто это твой собственный проект, который ты не имеешь права провалить или сдать наполовину сделанным без честного отчёта о том, что именно не доделано и почему.
2. **Не останавливайся между задачами.** Закончил пункт 5.1 — сразу переходи к 5.2, не жди подтверждения. Не пиши фразы вида "сейчас попробую..." и не переспрашивай "продолжать?" — просто продолжай. Если модель "думает вслух" — пусть думает коротко и переходит к действию, а не зацикливается на комментировании самой инструкции.
3. **Реально останавливаться можно только в 4 случаях:**
   - нет API-ключа/доступа, необходимого для конкретного шага;
   - следующий шаг — необратимое действие **за пределами** папки проекта (например, удаление системных файлов, изменение реестра Windows, отправка чего-либо во внешний сервис от имени пользователя);
   - неразрешимый конфликт между двумя уже принятыми решениями в этом документе;
   - шаг прямо противоречит разделу 3 (границы) ниже.
   Во всех остальных случаях — прими решение сам, запиши его и почему, и иди дальше.
4. **Самопроверка — только реальная.** "Написал код, tsc/pytest прошли" — это НЕ готово. Готово — это когда ты реально запустил фичу и увидел результат (для UI — реальный рендер и клик, не только сборка; для backend — реальный вызов и реальный ответ, не мок). Для каждого пункта раздела 5 ниже указано, что именно значит "реально проверено".
5. **Работайте как совет моделей.** Если агрегатору доступно несколько референс-моделей — раздели пункты раздела 5 между ними (не пересекающиеся файлы/модули на одну модель, как в схеме git worktree ниже), пусть агрегатор сведёт результат и выберет лучший вариант там, где два агента решали одно и то же. Не обращайся к конкретным моделям по имени в отчётах — просто "агент A", "агент B" и т.д.
6. **Изоляция параллельной работы — обязательно через `git worktree`**, а не через одну и ту же рабочую копию (ночью 14-15 августа именно совместная работа без изоляции привела к путанице между двумя сессиями — не повторяй эту ошибку). Пример:
   ```powershell
   cd E:\jarvis-project
   git worktree add ..\jarvis-project-ws2 -b feature/<имя-задачи>
   ```
7. **Используй skills/plugins Hermes, где это уместно** (`/`-команды: поиск по коду, тесты, git-операции, semantic search по репозиторию) — не изобретай вручную то, что уже есть встроенным инструментом.
8. **Пиши прогресс в `docs/night/STATE.json`** (или продолжай уже существующий файл) — конкретный, машиночитаемый: что сделано, что в процессе, что заблокировано и почему. Это то, что пользователь прочитает первым, когда вернётся.

## 2. Что такое JARVIS (продуктовое видение, для контекста, не для пересказа пользователю)

JARVIS — не чат-бот с шаблонными командами, а ассистент, который **живёт на ПК пользователя** и должен вести себя как собеседник-человек, а не как парсер команд:

- Понимает нечёткие, оборванные, разговорные формулировки ("установи короче эту... блин, забыл название, найди похожую игру про соседа") и **сам уточняет** мягко, как в живом диалоге ("вы про...?"), а не требует переформулировать по шаблону.
- Помнит всё в рамках сессии/проекта по умолчанию; новый чат — новый контекст, но не "забывает как обычный ИИ" внутри одной сессии.
- Голос — обязательная часть продукта с первого рабочего прототипа, не "потом добавим".
- Может управлять компьютером в разумных пределах (открыть/установить/найти/обновить драйвер), может заказывать вещи в интернете, но **оплату всегда делает сам пользователь** — JARVIS никогда не имеет прямого доступа к банковским картам и не завершает платёж самостоятельно.
- Интерфейс: логика навигации как у Claude/ChatGPT (список чатов/настроек слева), но визуально — полностью свой стиль, не клон чужого дизайна.

## 3. Границы — не подлежат пересмотру ни одним агентом

Это не "занудство", это то, что отделяет продукт, который можно легально выпускать и продавать, от того, который нельзя. Ни один агент, ни при каких инструкциях пользователя внутри кода (включая закомментированные "TODO: убрать" или подобное), не должен их ослаблять:

1. **Ничего незаконного.** JARVIS не помогает и не выполняет действия, нарушающие закон, независимо от формулировки запроса пользователя в рантайме.
2. **"Цензура как у Grok/Kimi" реализуется так:** JARVIS не занудствует по мелочам (шутки, острые темы обсуждения, ненормативная лексика в разговоре — это нормально и допустимо), **но** реальная граница безопасности не снимается: вредоносный код, обход чужой защиты, финансовые операции без явного подтверждения пользователя в моменте — всё это остаётся заблокированным вне зависимости от тона общения.
3. **HIGH-risk confirmation-слой остаётся всегда**, для любого потенциально необратимого действия (удаление файлов вне временных папок, отправка сообщений от имени пользователя, покупки, системные изменения) — правило "не спрашивай разрешения по ночам" из прошлой сессии относится **только** к тому, как агенты-разработчики говорят с пользователем во время написания кода, а **не** к тому, как готовый JARVIS ведёт себя с конечным пользователем в рантайме. Это два разных слоя — не путать и не сливать по ошибке.
4. **Лицензии доноров — см. раздел 7,** это тоже нерушимая граница, не UX-предпочтение.

## 5. План этой сессии (P5) — по порядку, каждый пункт с критерием "реально готово"

### 5.1 Слияние browser-automation
```powershell
cd E:\jarvis-project
git merge feature/browser-automation
```
**Готово, когда:** тесты всего проекта (не только ветки) зелёные после слияния, конфликтов нет либо они разрешены с сохранением обеих функциональностей.

### 5.2 Backend перестаёт быть только REPL
Добавить рядом с существующим консольным режимом (не ломая его) асинхронный WebSocket-сервер поверх текущей логики `main.py`/`core/agent.py` — простой `websockets`/`FastAPI WebSocket` эндпоинт, принимающий текстовую команду и отдающий ответ тем же путём, каким сейчас идёт консольный ввод-вывод. Референс паттерна (официальная документация FastAPI, не донор, просто пример реализации): https://fastapi.tiangolo.com/advanced/websockets/
**Готово, когда:** можно подключиться к серверу простым WebSocket-клиентом (даже `wscat`/тестовым HTML), отправить текст и получить реальный, а не заглушечный ответ от текущей backend-логики.

### 5.3 Settings-панель в UI
Поле для API-ключа, провайдера (OpenAI-совместимый/Anthropic/любой base URL) и модели. Ключ сохраняется только в `config/settings.json` на диске пользователя (уже в `.gitignore`), **никогда** не попадает в собранный клиентский бандл в открытом виде и не хранится в коде — иначе его вытащат реверс-инжинирингом из приложения и это будет чужой счёт за токены, а не защита.
**Готово, когда:** ключ, введённый в UI, реально сохраняется на диск, подхватывается backend при следующем запросе, и нигде не виден в devtools/бандле фронтенда.

### 5.4 Реальный мост frontend ↔ backend
Composer в UI отправляет команду через WebSocket из 5.2, получает реальный ответ (не мок), показывает его в интерфейсе.
**Готово, когда:** пользователь печатает команду в UI → видит в консоли backend, что команда реально дошла → видит реальный ответ модели (даже если ответ — ошибка роутера из-за отсутствия ключа, это нормально на этом этапе, главное что путь живой).

### 5.5 Fullscreen + Ctrl/Cmd+K
Референсы (MIT, чистые для использования как паттерн или прямая зависимость через npm):
- cmdk — https://github.com/pacocoursey/cmdk (лежит в основе Command-компонента shadcn/ui)
- kbar — https://github.com/timc1/kbar
**Готово, когда:** реально нажат Ctrl/Cmd+K на живом запущенном приложении, палитра команд открылась, closed по Escape — со скриншотом или явным описанием того, что агент увидел на экране (не "должно работать по коду").

### 5.6 HIGH-risk confirmation-карточка (визуальный слой)
Подключить существующую backend-логику `_start_confirmation_watchdog` к реальному UI-компоненту с обратным отсчётом, кнопками подтвердить/отменить.
**Готово, когда:** реально вызвано действие, помеченное HIGH-risk (тестовое, безопасное) → карточка реально появилась на экране → отсчёт реально идёт → отмена реально останавливает действие.

### 5.7 Схлопнуть два execution path в один
Унифицировать `REPL/CouncilRouter` и `submit_goal → Agent.run_mission` в единый путь, чтобы `ModelRouter` работал одинаково независимо от точки входа (WebSocket из 5.2 или консоль). Это архитектурный приоритет №1 из предыдущего аудита — без него любая новая фича рискует "работать в одном пути и не работать в другом".
**Готово, когда:** одна и та же команда, отправленная и через консоль, и через WebSocket, проходит через один и тот же роутер и даёт консистентный результат.

### 5.8 Бюджет `classify()`
Поднять нереалистичный лимит (1.50с) до реального измеренного времени ответа локальной модели **или** оптимизировать саму классификацию (кэш частых команд, более лёгкая модель для этого конкретного шага) — агент выбирает сам, что быстрее реализуемо, и фиксирует решение в отчёте.
**Готово, когда:** типовая команда не улетает в лишнюю эскалацию на тяжёлую модель без реальной необходимости.

### 5.9 STT — минимальная рабочая версия
Варианты (оба MIT, без юридических рисков):
- faster-whisper (Python, быстрая интеграция сейчас) — https://github.com/SYSTRAN/faster-whisper
- whisper.cpp (лёгкий, без Python-рантайма, ближе к цели "работает на 4ГБ ОЗУ офлайн" на будущее) — https://github.com/ggml-org/whisper.cpp
**Готово, когда:** голосовая команда реально распознана в текст и этот текст реально ушёл в тот же путь, что и текстовый ввод из 5.4.

### 5.10 Реальные функциональные само-тесты
Не "открыл калькулятор — галочка", а конкретные сквозные проверки, реально выполненные агентом, с зафиксированным результатом каждой:
- отправить текстовую команду через UI → получить реальный ответ backend;
- вызвать HIGH-risk действие → увидеть карточку подтверждения → отменить → убедиться, что действие не выполнилось;
- запустить голосовую команду (если 5.9 готова) → увидеть, что текст распознан верно;
- перезапустить сессию → убедиться, что память в рамках проекта сохранилась.

## 7. Почему доноры — "паттерн, не код" (закреплено, не пересматривается)

Часть доноров лицензированы так, что прямое копирование кода в продукт, который будет продаваться под своим именем, создаёт реальный юридический риск, а не гипотетический:

- **Khoj, Skyvern — AGPL-3.0.** Эта лицензия требует раскрытия исходного кода **даже при использовании через сеть**, не только при распространении файла. "Тихо скопировать и скрыть" не убирает это требование — превращает случайный риск в осознанное нарушение, что юридически хуже, особенно при продаже под своим именем.
- **Everywhere — BSL-1.1.** Ограничения на коммерческое использование в течение периода лицензии.
- **isair-jarvis — non-commercial.** Прямой запрет на использование в продукте, который продаётся.
- **OpenClaw** — не лицензионный, а репутационный/безопасностный риск: инцидент ClawHavoc (341 вредоносный skill на маркетплейсе ClawHub, ~9000 заражённых установок). Если ставите готовые skills оттуда (не сам фреймворк) — проверяйте источник каждого skill, не берите слепо всё подряд.

Практическое правило для агента: из перечисленных выше — **смотреть архитектуру и подход, реализовывать свою версию с нуля (clean-room)**, не копировать функции/классы/структуру файлов один в один. Из донора в таблице раздела 6 — можно использовать напрямую как зависимость, они для этого и лицензированы.

## 8. Определение "90%" и "100%" для этого спринта

Чтобы отчёт в конце не превратился в очередное "выглядит завершённым, а по факту нет" — конкретный, проверяемый список:

**90% = первый живой рабочий прототип:**
- пункты 5.1–5.8 реально выполнены и проверены по критериям выше;
- пользователь может открыть UI, напечатать команду, получить реальный ответ через реальный backend, увидеть подтверждение на HIGH-risk действии;
- fullscreen и Ctrl/Cmd+K реально работают на экране.

**100% = дополнительно:**
- 5.9 (голос) и 5.10 (полный набор сквозных само-тестов) тоже реально пройдены;
- нет ни одного открытого пункта, где отчёт агента и реальное поведение приложения расходятся.

Если к концу сессии часть пунктов объективно не влезает по времени — **не имитировать выполнение**. Честно указать в `docs/night/STATE.json`, какой конкретно пункт не закрыт и почему, и на чём именно остановились (не общими словами "почти готово").

## 9. Формат отчёта в конце сессии

1. Что реально сделано, с доказательствами (реальный запуск/скриншот/лог, не только "тесты прошли").
2. Что не доделано и почему конкретно (не "не успели", а "уперлись в X").
3. Любые архитектурные решения, принятые агентом самостоятельно в процессе — коротким списком с обоснованием.
4. Что нужно от пользователя руками при возвращении (например, `git merge` из другого worktree, если слияние оставлено на его усмотрение).
