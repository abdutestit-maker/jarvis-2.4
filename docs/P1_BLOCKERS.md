# P1 — Зафиксированные блокеры / инфра-задачи (НЕ в этом спринте)

Этот документ фиксирует задачи, которые вышли за рамки клиентского спринта P1
и требуют отдельной инфраструктурной работы. Они НЕ блокируют поставку P1
(клиент уже не вшивает ключи автора), но должны быть закрыты до продакшн-релиза
облачной эскалации.

## BLOCKER-1 (критично): Локальный proxy-сервер для облачных ключей

**Статус:** НЕ РЕАЛИЗОВАН в этом спринте (отдельная инфра-задача).
**Причина:** архитектурное решение владельца — ключ автора НЕ должен лежать
в клиенте J.A.R.V.I.S. на пользовательской машине (§1.4 «НИКАКИХ вшитых ключей»).

**Что сделано в P1 (клиентская часть):**
- Создан `core/llm/proxy_client.py` — `ProxyLLMClient`, который шлёт запросы
  НЕ напрямую на endpoint провайдера, а на локальный proxy-сервер
  (`settings.proxy.endpoint`, напр. `http://127.0.0.1:8787/v1`).
- В заголовках клиента НЕТ `Authorization: Bearer <api_key_автора>`. Вместо
  этого клиент шлёт только локальный `proxy_token` (отдельный, не секретный
  маркер доступа к локальному proxy) — `X-Jarvis-Proxy-Token`.
- Реальный ключ автора живёт ТОЛЬКО на proxy-сервере и добавляется сервером
  при пробросе запроса к провайдеру.

**Что осталось (инфра-задача, вне P1):**
1. Написать сам proxy-сервер (минимум: HTTP-прокси, который принимает
   запрос от клиента, подставляет `Authorization: Bearer <key_автора>` из
   своего защищённого хранилища, форвардит на endpoint провайдера, возвращает
   ответ). Хранить ключ в OS keychain / vault, НЕ в файле в репозитории.
2. Реализовать ротацию/обновление ключа на сервере без пересборки клиента.
3. (Опционально) Менеджер биллинга/лимитов на сервере, чтобы клиент не
   ушёл в неограниченный расход.

**DoD для BLOCKER-1 (когда считать закрытым):** клиент работает сквозь
proxy-сервер; grep по клиенту НЕ находит `api_key_автора` в заголовках;
ключ автора присутствует только в хранилище сервера.
