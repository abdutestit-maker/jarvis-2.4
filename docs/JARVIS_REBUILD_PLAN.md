## 0. TL;DR

- **Жалоба «две ИИ в связке (qwen3 1.7b + deepseek-r1 1.7b) — медленно и тупо» верна как боль, но диагноз был не там.** В коммите нет per-turn связки двух моделей: offline-режим гоняет ОДИН core (Qwen3-4B), а 1.7B — это фоновый Shadow. Связка живёт в твоём личном `config/settings.json` (он в `.gitignore`, ИИ его читать не может — фикс передан в handoff).
- **Корневая ошибка паттерна «fast + reasoning на двух 1.7B»**: двойная латентность + reasoning-налог на простых запросах + эскалация «вверх» в модель, которая НЕ умнее. Это архитектурный тупик, а не вопрос подбора весов.
- **Правильно: один сильный core под железо пользователя + крошечный router + reasoning строго по требованию + streaming + instant ack + speculative decoding.**
- **Честно про «1 ГБ ОЗУ и умеет всё, локально, без API»**: так не бывает (§3). Решение — не врать пользователю, а адаптировать модель под железо (см. `core/llm/hardware_profile.py`) и честно разграничить, что работает офлайн, а что требует докачки модели/ресурсов.

## 2. Что РЕАЛЬНО в модельном слое (проверено по коду)

Файлы: `config/settings.py`, `config/settings.example.json`, `core/llm/factory.py`, `core/llm/tiers.py`, `data/models/`.

- **На диске лежат:** `qwen3-4b-instruct-q5_k_m.gguf` (2.9 ГБ), `Qwen3-1.7B-Q6_K.gguf` (1.7 ГБ), голоса Piper. **DeepSeek-R1 на диске НЕТ** — только как удалённый провайдер (без ключа недоступен).
- **`offline_mode=true` (шаблон):** `get_provider()` возвращает `local` для ВСЕХ тиров; `factory.py` в offline игнорирует строки `model_tiers` (`qwen-1.7b-local` и т.п.) и берёт файл из `get_local_config(role)`. Для FAST/ANALYST/ARCHITECT это `local_model` (4B), для CODER — `local_coder_model` (пустой → фолбэк на 4B). **Итог: все тиры = один Qwen3-4B.**
- **Qwen3-1.7B** реально используется только фоновым `core/shadow/generator.py`. Его путь в конфиге указывал на несуществующий `qwen3-1.7b-instruct-q4_k_m.gguf` → **баг, Shadow молча деградировал.** Починено в этой сессии (см. §7).
- **Опасный анти-паттерн в шаблоне:** `model_tiers.analyst/coder/architect = "qwen-1.7b-local"`. В offline это косметика, но если кто-то выключит `offline_mode`, эскалация формально ведёт в модель МЕНЬШЕ и ТУПЕЕ, чем FAST. Логически перевёрнутая лестница — так делать нельзя.

## 3. Честное ограничение: «1 ГБ + умеет всё + локально + без API»

Это физически несовместимые требования. Прямо и без сказок:

- Модель, которая «делает презентацию, ставит приложение по видео на чужом языке, мгновенно рассуждает», — это уровень минимум 4B–8B (а для видео — ещё и мультимодальная VLM). Такой GGUF — **3–9 ГБ на диске и 5–20 ГБ памяти при работе.** В 1 ГБ ОЗУ это не влезет никогда.
- «Джарвис-проекты в 1 ГБ ОЗУ», которые ты видел, — это одно из двух: (а) тонкий клиент, который ходит в облачный API (значит, кто-то платит за модель), либо (б) парсер команд по ключевым словам, который «умным» только выглядит. Полноценного офлайн-интеллекта в 1 ГБ не существует.
- Без API-ключей (твоё условие) весь интеллект обязан быть локальным → упирается в железо пользователя.

**Как примиряем (реалистичный продукт):**

1. **Приложение лёгкое, модель — отдельно.** Инсталлятор маленький; модель докачивается под железо при первом запуске (`hardware_profile` уже возвращает `download_required` + имя файла).
2. **Адаптивная лестница (реализовано):** слабый ноут (4 ГБ, без GPU) → Qwen3-0.6B; офис 8 ГБ → 1.7B; десктоп 16 ГБ / RTX 2060+ → 4B; RTX 3080 → 8B; RTX 4090 → 14B. Один код — каждый получает максимум от своего железа.
3. **Честная деградация возможностей.** «Мгновенный чат» — везде. «Сделать презентацию/разобрать длинное видео» — только там, где модель и память это тянут; на floor-железе Джарвис прямо говорит, что задача превышает локальные возможности, а не выдаёт мусор.
4. **Тяжёлую мультимодальщину (видео) — модульно.** Отдельный опциональный VLM-пакет, который ставится только на способное железо.

Это и есть «запустится у каждого»: у каждого — свой потолок, но продукт не падает и не врёт.

## 4. Целевая архитектура модельного слоя

```
Вход (текст/голос)
   │
   ▼
[ Router ]  ← Qwen3-0.6B/1.7B ИЛИ детерминированные правила (~50-100 мс)
   │  классы: command | chat | reasoning | tool
   ├── command  → детерминированный tool, БЕЗ LLM        (мгновенно)
   ├── chat     → CORE (адаптивный: 0.6B..14B), streaming (быстро)
   ├── reasoning→ CORE в режиме «думать» ИЛИ фон-миссия  (по требованию)
   └── tool     → CORE + нативный function-calling
   │
   ▼
[ Ответ ] — instant ack (≤100мс) → streaming токенов в TTS/UI
```

Принципы:
1. **Один сильный core на данном железе.** Никаких «двух моделей на каждый запрос».
2. **Маленькая модель = router/draft, НЕ «умный тир».** Эскалация всегда идёт в модель ≥ по силе, никогда «вниз».
3. **Reasoning — по требованию.** `<think>`-режим включается роутером только для реально многошаговых задач; «который час» его не платит.
4. **Speculative decoding** (llama.cpp `--model-draft`): draft Qwen3-1.7B ускоряет декод core 4B/8B, когда хватает VRAM держать обе. Управляется `hardware_profile` (`draft_model`).
5. **Instant ack + streaming** обязательны в живом пути — «ощущение тупняка» лечится восприятием, а не только tok/s.
6. **Hardware-adaptive** через `core/llm/hardware_profile.py` (реализовано): `detect_hardware()` + `recommend_profile()`.

## 5. Мёртвый код / что консолидировать (актуализировано)

| Транспорт frontend↔Python | по-прежнему требует проверки (`core/ws_server` есть) | Codex: подтвердить живой WS-мост, добить UI |

## 6. Roadmap возможностей «чтобы продавалось»

Разбито на то, что нужно для витринных сценариев. Детали и порядок — в `docs/CODEX_HANDOFF.md`.

1. **Model auto-download** (`core/utils/model_manager.py` + манифест): качает нужный GGUF по `hardware_profile`, с проверкой SHA и прогресс-баром. Без него «запустится у каждого» неполноценно.
2. **Speculative decoding в `LocalQwenBackend`**: поддержка draft-модели.
3. **Wire `hardware_profile` в конфиг/фабрику**: при старте — авто-подстановка `gguf_path/n_gpu_layers/n_ctx`.
4. **Нативный function-calling** вместо regex `TOOL_CALL:` (надёжность действий).
5. **STT (голосовой ввод)**: `faster-whisper` (в конфиге уже заложен) — сейчас заглушка.
6. **Artifact generation**: `python-pptx`/`python-docx` — сценарий «сделай презентацию».
7. **Computer-use / браузер**: Playwright + set-of-marks — «поставь приложение по видео», «сделай за меня в браузере».
8. **Frontend transport**: довести `jarvis/` до живого WS-моста к `core.ws_server`.
